# 播放中途重开导致进程 abort：根因、复现、修复与残余风险

> 结论先说：**根因不是"重开"本身，而是"跳转时由解封装线程去冲刷解码器"**。
> AI 播放顾问"换参数重开"之后紧跟一次 `跳转(位置)`，那一次跳转正好撞上解码线程在
> `avcodec_send_packet`，libav 的帧级多线程解码器断言失败 → `abort()` → 整进程 SIGABRT。
> 已复现（与用户真机 core **逐帧同址**）、已修、已真机压测验收。

## 三、修了什么

### 1. 世代号（generation）——`wangpan/player/引擎.py`

* 每次 `打开()` 自增世代号，把这一代的资源装进一个 `_播放代` 对象
  （输入 / 视频解码器 / 音频解码器 / 音频输出 / 时钟 / 停 / 暂停 / 两个队列 / 线程表 / 流世代）；
* 线程启动时把这一代**作为参数带进去**（`target=函数, args=(代,)`），
  此后只认自己手里这一份，**再也不读 `self.输入`/`self.视频`**；
* `_该停(代)` 的判据：`代.停.is_set()`（用户要停）**或** `代 is not self._本代`
  （有人开了新一代）。老线程一发现"我不是当前代"就退出，
  **退出前不再发任何 libav 调用**。

为什么必须有：老代码在 join 超时后会 `self._停.clear()` 并返回，老线程于是接着跑，
而 `self.输入/self.视频` 已经换成新一代的对象 —— 两个线程共用一个 `AVFormatContext`
就是 abort。

### 2. 跳转不再跨线程冲刷（这是本次崩溃的直接正解）

* `_执行跳转()`（跑在解封装线程里）**只做**：`avformat_seek_file` → 排空队列 →
  `流世代 += 1` → 复位时钟。**不再调用 `解码器.冲刷()`**；
* 解码线程拿到带新流世代的包时，由**它自己**调 `冲刷()`（`引擎._按需冲刷`）；
* 解码器加了一把可重入锁（`解码._基础解码器.用锁`），
  `送包/收帧/取帧/冲刷/关闭` 全在锁里 —— 界面线程的"逐帧"也走同一把锁；
* 倍速：`音频解码器.设置倍速` 现在**只登记请求**，重建重采样器由音频线程在
  `_准备重采样` 的安全点上做（原来界面线程直接 `swr_free`，和 `swr_convert` 并发 =
  同一类 use-after-free）。

### 3. `停止()` 真的等到线程死透

* `打开()` 第一步永远是 `停止()`，并且**检查返回值**；
* 线程 join 有超时（默认 6s）；**超时就一个字节都不释放**，把整代资源放进 `_退役们`
  保管（并写日志说明代价），下次 `打开/停止` 时若线程已退出就补做释放；
* 释放顺序固定：队列里的包 → 音频输出 → 解码器 → 格式上下文；
* `打开/播放/停止` 共用一把 `_开停锁`：**两个线程不可能同时重开**
  （真机 22:04:08 就是同一秒两条参数更新）。

### 4. AI 自动重载安全化——`wangpan/ui/播放会话.py`

* **去抖**：两次自动重开间隔 < 8s 时只记参数、不重开（`自动重载最小间隔秒`）；
* **等安全点**：`安全点查询` 由界面注入；正在**拖进度条**或**搬独立窗口**时，
  重开排队（`_待重载`），由播放页 16ms 定时器调 `推进待办()` 在安全点上落地 ——
  **不硬插一次 `打开()`**；
* `播放器窗口._搬入/_搬回` 会调 `内核页.标记窗口搬动(True/False)`，
  搬完延迟 260ms 放行（等 Qt 那串 resize 过去）。

### 5. 缩略图

`缩略图器` 内部加锁（取图与关闭不并发）——对应 17:50 那次 `V2-缩略图` 崩在
`avcodec_send_packet`（同一类"一个 libav 上下文被两个线程用"）。

## 四、验收

* 全量单测：`1406 → 1429` 条（新增 `tests/test_重开与世代.py` 14 条 +
  另一位同事的 9 条），**只有 1 条失败且与本次改动无关**
  （`tests/test_可移植性.py` 报 `wangpan/scrape/服务.py:170` 的注释里写死了本机家目录，
  那是同事正在改的文件、未提交改动引入的；本文件与本次新增代码都不含本机绝对路径）；
* 压测：真网盘 4K60 HEVC 直链、硬解照开（每轮统计里都能看到 `VAAPI 硬解…硬解帧 N>0`），
  **最终代码上跑 24 轮（阶段A 14 + 阶段B 5 + 阶段C 5）不崩，退出码 0，
  结束后无残留线程；阶段 A 14/14 轮都真解出了帧（共 351 帧）**；
  另有 32 轮（A20+B6+C6，有效 16/20）与 20 轮（A12+B4+C4，有效 12/12）两次运行同样不崩。
  同一命令在修复前**第 2 轮必崩**（退出码 134，SIGABRT，栈与用户真机 core 同址）。

## 五、没解决的残余风险（如实说）

1. **超时退役会泄漏一代资源**：如果某个线程 6 秒还没退出（例如卡在
   PulseAudio 的 `pa_simple_write` 里），那一代的 `AVFormatContext`/解码器/音频设备
   就**故意不释放**（换来的是绝不悬垂）。正常机器上不会走到这条路（压测 32 轮退役数为 0），
   但极端情况下会漏内存与一个音频流。
2. **跳转后可能闪一帧旧画面**：跳转只把"流世代"往前推，解码线程手里那帧（跳转前取的）
   仍可能被发布一次。引擎已经把 `_最新帧` 清掉，且这种帧通常会被"太晚了"丢掉，
   但没有结构性禁止。想彻底消除得让解码线程在发布前核对流世代。
3. **安全点只覆盖"拖动"和"搬窗口"**：其他界面动作（切侧栏、全屏、切集）
   没有接线到 `标记窗口搬动`，那些时刻仍可能发生自动重开（有去抖兜着）。
4. **跨进程/跨库的 `abort()` 无法被 Python 捕获**：这次是 libav 的 `av_assert0`，
   即使加了世代号与锁，也只能保证"我们不再制造这个竞态"，
   不能保证 libav 自身在网络抖动下的所有断言都不触发（例如
   `Could not find ref with POC` 这类**警告**仍会出现在 seek 之后，属正常现象）。
5. **压测覆盖率的自证**：32 轮里有 4 轮阶段 A "一帧都没解出来"（压迫太密 +
   恰好停在暂停），脚本会把这几轮标出来 —— 也就是说这 4 轮没真正压到解码路径，
   有效轮次是 16/20（另有两次 12/12 的运行）。
