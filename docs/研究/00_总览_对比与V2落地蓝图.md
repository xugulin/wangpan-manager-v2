## 〇、先把一个误会说清：Vidhub 的链接

你给的 <https://github.com/nabilfarhann/Vidhub> **经核实不是影音播放器 VidHub**，而是一个
**PHP 写的"YouTube 克隆"视频分享网站**（89 星，语言 PHP，描述 "Video sharing website (YouTube clone) with PHP"）。
两者同名但完全是两回事：

| | 你给的仓库 | 大家说的 VidHub（影音 App） |
|---|---|---|
| 是什么 | 自建视频分享网站（上传/播放/评论的 Web 站） | iOS/iPadOS/macOS/tvOS 上的**影音播放器 + 媒体库** |
| 语言/形态 | PHP + Web | 闭源商业 App（**没有开源仓库**） |
| 与刮削的关系 | 无自动刮削 | 有：连 Emby/Jellyfin/Plex/WebDAV/SMB + TMDB 刮削 + 海报墙 |

所以研究 VidHub 只能靠**官方文档/App Store 说明/官网**这类公开信息（分册里逐条标了出处与可信度），
**拿不到源码**。若你想研究的是开源实现，同类可看：Jellyfin（服务端）、Kodi 的 scraper 插件、
`tinyMediaManager`（Java 桌面刮削器）、`MoviePilot`（Python，中文圈常用，带 TMDB 刮削 + 做种/整理）。

### 1.2 匹配算法（已读源码，确认）

`DanmakuMatcher` 是**函数式接口**，内置两种实现：

* `DanmakuMatchers.first()` —— 直接取第一条（最省事，质量最差）
* `DanmakuMatchers.mostRelevant(targetSubjectName, targetEpisodeName)` ——
  对候选项算 **`levenshteinDistance(条目名, 目标条目名) + levenshteinDistance(集名, 目标集名)`**，
  取**距离最小**的那个。就是"标题 + 集名的编辑距离之和"这种朴素但有效的打分。

DanDanPlay 侧的匹配是**服务端算**的（我们只要把素材递上去）：见 `danmaku/dandanplay/dandanplay.http`：

```http
### 匹配剧集
POST https://api.dandanplay.net/api/v2/match
Content-Type: application/json

{ "fileName": "[爱恋字幕社][10月新番][葬送的芙莉莲][Sousou no Frieren][01][1080P][MP4][GB][简中]",
  "fileHash": "0805b7f980d59b64dd382fe00b3ba2a5",
  "fileSize": 129000,
  "videoDuration": 1440,
  "matchMode": "hashAndFileName" }

### 取弹幕
GET https://api.dandanplay.net/api/v2/comment/176170001?chConvert=0&withRelated=true
```

要点：**文件名原样送上去**（含字幕组/季集信息）、**文件哈希 + 大小 + 时长**一起送（`matchMode=hashAndFileName`），
匹配完拿 `episodeId` 去取弹幕；`chConvert` 是**简繁转换**开关，`withRelated` 会把关联弹幕一起返回。

> ⚠️ 我核实到的：接口与请求体如上（来自仓库里的 `.http` 样例）。
> "fileHash 具体取文件前多少 MB 的 MD5"这一步我没在这两个文件里核实，分册里若查证到会写上；**不许当成已知**。

### 1.3 渲染与观感参数（`DanmakuConfig.kt` 原文默认值）

| 参数 | 默认 | 含义 |
|---|---|---|
| `speed` | **88f** | 弹幕从右到左穿过屏幕的时间（单位 dp/s，即速度） |
| `safeSeparation` | **36.dp** | 两条弹幕之间**避免重叠**的最小间距 |
| `displayArea` | **0.25f** | 弹幕只占屏幕高度的比例（0.25 = 上 1/4 …按实现是显示区域比例） |
| `enableColor` | true | 关掉则彩色弹幕一律显示为白色 |
| `enableTop` | true | 顶部固定弹幕 |
| `enableFloating` | true | 滚动弹幕 |
| `enableBottom` | **false**（4.4.0 起默认关） | 底部固定弹幕 |
| `isDebug` | false | 打印发送/处理信息 |
| `style` | `DanmakuStyle.Default` | 字号、描边宽度等文本样式 |

轨道实现里还有两个关键设计（`FloatingDanmakuTrack.kt` 注释里写明）：

* **按长度调速度**：给出一个 `baseSpeedPxPerSecond`，**长度等于基准宽度的弹幕速度 = 1×**，
  更长的会**加速**；`DanmakuTrackProperties.speedMultiplier` 默认 **1.14**（长度是基准 2 倍时的倍率），
  代码里用 `log/pow` 做平滑曲线 —— 目的是"长弹幕不要挡太久"；
* 弹幕出队（消失）靠 **tick 里的逻辑帧检测** + `clearAll()`，不是靠逐条定时器。

### 1.4 已核实的实现细节（读源码得到，可直接照做）

**① DanDanPlay 的鉴权与签名（`danmaku/dandanplay/src/commonMain/kotlin/DandanplayClient.kt:56-70`）**

```kotlin
header("X-AppId", appId)
val time = currentTimeMillis() / 1000
header("X-Timestamp", time)
```

### 1.5 弹弹play 官方开放弹幕网络（权威原文，实施必须按这个来）

官方文档：<https://doc.dandanplay.com/open/>（我通读并摘录，2026-07-20 更新版）

**① `fileHash` 到底是什么（这条我先前标"未找到"，现在有官方答案）**

> Hash计算方式：使用文件前 **16MB（16x1024x1024 字节）** 数据计算 **MD5**

官方还给了**测试向量**：一个样例视频，其前 16MB 的 MD5 = `658d05841b9476ccc7420b3f0bb21c3b`
（视频下载页：<https://kaedei.lanzouo.com/itjCq30geele>）—— 我以后写 V2 的哈希函数就有对拍物了。

**② 签名（签名验证模式，官方推荐客户端用这个）**

```
X-AppId:     <AppId>
X-Timestamp: <Unix 秒>
X-Signature: base64(sha256(AppId + Timestamp + Path + AppSecret))
```

`Path` = **接口路径部分**（以 `/` 开头，**不含协议/域名，也不含 `?` 后的查询串**；官方建议全小写、不做 URL 编码）。
例：访问 `https://api.dandanplay.net/api/v2/comment/123450001?withRelated=true`
→ 参与签名的 `Path` 是 `/api/v2/comment/123450001`。

Python 落地（我自己按官方算法写的，与官方示例一致）：

```python
import base64, hashlib, time
def 签名(app_id: str, path: str, app_secret: str, 时间戳: int | None = None) -> dict:
    时间戳 = int(time.time()) if 时间戳 is None else int(时间戳)
    数据 = f"{app_id}{时间戳}{path}{app_secret}".encode()
    return {"X-AppId": app_id, "X-Timestamp": str(时间戳),
            "X-Signature": base64.b64encode(hashlib.sha256(数据).digest()).decode()}
```

还有**凭证模式**（`X-AppId` + `X-AppSecret`），官方说**只建议服务器端用**；客户端/开源客户端
**不要硬编码 AppSecret**（官方明确给出两条做法：自建服务端转发，或用占位符 + CI 构建时注入）。

**③ 公开接口 vs 受限接口（这条决定我们能做到哪一步）**

| | 内容 | 鉴权 |
|---|---|---|
| **公开接口** | **文件识别 `/api/v2/match`、搜索 `/api/v2/search`、获取弹幕 `/api/v2/comment`** | 新应用默认可用（**发送弹幕不在其中**） |
| **受限接口** | 关注、播放历史、**发送弹幕 `/api/v2/comment/{episodeId}/app`** | 需要**用户 JWT**（`Authorization` 头），且官方明确"**当前暂不开放受限接口的访问权限**" |

⇒ 结论（对我们很重要）：**"取弹幕"能做，"发弹幕"目前拿不到权限**（除非专门申请）。
所以 V2 的弹幕第一版应当**只读**；要发就发到 Animeko 那类自有服务或仅本地保存。

**④ 调用流程（官方原文的三步）**

1. 打开视频时调 **`/api/v2/match`**（传**文件名 + hash + 大小 + 时长**）→ 返回"此文件可能是…"列表 →
   **让用户在列表里挑一个**（官方明确说需要用户选择）→ 得到并保存 **`episodeId`**
   （一个节目可关联多个文件，一个文件只关联一个节目）；
2. 用 `episodeId` 调 **`/api/v2/comment/{episodeId}?withRelated=true`** 取弹幕
   （`withRelated=true` = 整合第三方站点弹幕）；
3. 发送：**`/api/v2/comment/{episodeId}/app`**（受限，见上）。

**⑤ 错误与缓存（官方要求）**

* 业务错误可能藏在 **HTTP 200** 里：`{"success": false, "errorCode": 1, "errorMessage": "…"}`；
  401 = 缺鉴权头；403 = 缺头/时间戳偏差过大/AppId 或 AppSecret 无效/签名不匹配/被屏蔽 IP，
  细节在 **`X-Error-Message`** 头里（取值：`Missing Authentication Headers`、`Invalid Timestamp`、
  `Invalid AppId`、`Invalid Signature`、`Invalid AppSecret`）；
* **缓存建议（原文）**：一般 2–6 小时；当季热门更新当天 0.5–1 小时；非当季 12–24 小时；老番 2–7 天；
* 速率：**不硬性限频**，但搜索/取弹幕有检测机制，过量会被拦（2026-06-25 起还有分层额度）；
* 合规：**禁止**"批量下载弹幕/下载数据库"、禁止未授权商用；若以他们的数据为主要弹幕来源，
  **弹幕功能必须对所有用户免费**。

### 1.8 渲染引擎要点（另一路深挖 + 我自己的源码核对，两处结论一致）

Animeko 的弹幕渲染**不是**"每条弹幕一个定时器"，而是"**位置是帧时间的纯函数**"：

* **位置算法**：某条滚动弹幕在时刻 `t` 的 x 坐标 = `f(t)`（由它进入屏幕的时间与速度直接算），
  **不做积分、不累积误差** —— 丢帧/卡顿后位置依然正确，这是最值得抄的一条；
* **防重叠判据**（很巧）：新弹幕能不能放进这条轨道，看
  **「前一条弹幕的尾部飞出屏幕的剩余时间」是否大于「新弹幕头部飞出屏幕的剩余时间」** ——
  这样即使两条速度不同也不会追尾（比"最小间距"更严谨）；
* **插入**：轨道内按时间**二分**找位置，只比较相邻两条（不是遍历整条轨道）；
* **速度模型**：长弹幕按 `1.14^(log2(宽度/基准宽度))` 加速（就是配置里的 `speedMultiplier=1.14`），
  再叠加 **±8.75% 的随机抖动**（避免多条弹幕整齐划一像列队）；
* **每条弹幕预渲染成一张带描边的 bitmap 缓存**（Skia Surface / ARGB_8888），每帧只 `drawImage` ——
  文字量大的时候这是数量级的差别；QPainter 版对应 `QPixmap` 缓存（key = 文本 + 字号 + 颜色）；
* **帧时间平滑（PLL）**：`FrameTimeSmoother` 是个简化**锁相环** —— EMA 估计帧周期 + 相位误差回授 0.1、
  单帧修正不超过周期的 20%、超过 250ms 直接透传。桌面端（Skiko/Qt）帧回调时间戳会抖，
  **不做这个平滑就会看到弹幕一顿一顿**；
* **时间轴语义**：暂停时**帧循环不启动**（时钟停走）；seek 阈值 `3s × 播放倍速`、回溯装填 `20s`；
  **弹幕滚动速度不随倍速变化**（1.5 倍速看时弹幕不会飞得更快）；
* **关键常量**：速度 88 dp/s、安全间距 36dp、显示区域 0.25、字号 18sp/字重 W600/透明度 0.8/描边 4f、
  固定弹幕停留 5000ms、回溯装填 20s、会话心跳 50ms、清理心跳 1000ms、时间轴偏移范围 ±30s；
* **它没有的交互（我们可以做得更好）**：弹幕列表项**不可点击**（点了不能跳到那一刻）、
  画布**完全没有指针事件**（不能点弹幕/长按复制/举报）、进度条**没有弹幕密度预览**、
  多源弹幕**不去重**（同一句话会出现两遍）。

### 1.9 两条被独立验证过的"负面结论"（省得你再去踩）

| 说法 | 核实结果 |
|---|---|
| Animeko 会算"文件前 16MB 的 MD5"来做 hash 匹配 | **没有实现**。4 条独立证据：① `DandanplayClient.matchVideo()` 收了 `fileHash` 形参却**从不写进请求体**，`matchMode` 硬编码 `"fileNameOnly"`；② `SearchDanmakuRequest.fileHash` 默认值是占位符 `"aa".repeat(16)`，运行时**恒等于 32 个 a**；③ 全仓库 `grep hashAndFileName` 只命中手写样例 `dandanplay.http`；④ 没有任何读文件头的代码。而**官方 swagger 明确**：`fileHash` = 前 16MB 的 32 位 MD5、`matchMode ∈ {hashAndFileName, fileNameOnly, hashOnly}`、`fileName` **不含目录与扩展名**。⇒ **这是我们能比它做得好的地方**（本地播放器稳定有文件，读头算 MD5 很便宜） |
| 仓库简介里的"弹幕云过滤" | **当前源码里不存在**（两路独立 grep：`云过滤/云屏蔽/cloudFilter` 全部 0 命中；官网功能页原文是"AI 团队将**逐渐推进**弹幕云过滤功能"；其 OpenAPI 里与过滤相关的只有 `/v2/pfrule`，那是 **BT peer 过滤**，与弹幕无关）。⇒ 无可搬实现，要做得自己起服务端下发规则 |
| 屏蔽"关键字/发送者"、点赞、举报 | **都没有**。过滤只有**正则黑名单**（`DanmakuRegexFilter{id,name,regex,enabled}` + 全局开关，`Regex(IGNORE_CASE).find()`，可导入导出 JSON）。`senderId` 只用来判"是不是自己发的"（自己的加下划线）与来源分类 |

## 二、Jellyfin 的目录/命名规范（刮削的地基，已逐字核对官方文档）

### 2.1 电影

```
Movies
├── Best_Movie_Ever (2019)                  ← 文件夹名 = "片名 (年份) [数据源ID]"
│   ├── Best_Movie_Ever (2019).mp4          ← 文件名与文件夹同名（可带年份/ID）
│   ├── Best_Movie_Ever (2019).nfo
│   ├── Best_Movie_Ever (2019).en_us.srt
│   ├── cover.png
│   └── theme.mp3
└── Movie (2021) [imdbid-tt12801262]        ← 直接带数据源 ID，匹配最稳
    ├── backdrop.jpg
    └── VIDEO_TS/…
```

* 命名格式：`Movie Name (year) [metadata provider id]`；年份与 ID **可选但强烈建议**
  （ID 形如 `[imdbid-tt00000000]`，剧集/季/集都能带）；
* **多版本**：同一文件夹里"文件名必须以**文件夹名逐字符开头**"，再用 ` - `、`.`、`_`、`[ ]` 接版本标签：
  `Movie (2021) [imdbid-…] - 2160p.mp4` / `- 1080p.mp4` / `- Directors Cut.mp4`；
  排序规则：**分辨率名降序优先**（`2160p > 1080p > …`），其余按字母序；
* **多段**：`-cd1/-cd2`、`-part1`、`-pt1`、`-disc1`、`-disk1`（分隔符可用空格/`.`/`-`/`_`）；
* **番外/花絮**：子目录 `behind the scenes`、`deleted scenes`、`interviews`、`scenes`、`samples`、
  `shorts`、`featurettes`、`clips`、`other`、`extras`、`trailers`、`theme-music`、`backdrops`；
  或文件名后缀 `-trailer`、`.trailer`、`-behindthescenes`、`-deleted`、`-featurette` 等；
* **3D**：`3D` + `hsbs/fsbs/htab/ftab/mvc`（大小写不敏感，需被空格/`-`/`.`/`_` 包住）。

### 2.2 剧集（你说的"自动按季分集"就是这套）

```
Shows
├── Series Name A (2010)                    ← 剧文件夹："剧名 (年份) [ID]"
│   ├── Season 00                           ← 特别篇固定放 Season 00
│   │   ├── Series Name A S00E01.mkv
│   ├── Season 01                           ← 必须写 "Season NN"（官方明确：**别缩写成 S01/SE01**）
│   │   ├── Series Name A S01E01-E02.mkv    ← 一文件多集用 "-"
│   │   ├── Series Name A S01E03.mkv
│   │   └── Series Name A S01E04.mkv
│   └── Season 02
│       ├── Series Name A S02E03 Part 1.mkv ← 一集多段
│       └── Series Name A S02E03 Part 2.mkv
```

* 季号**建议补零**（`Season 5` → `Season 05`）；**不要把剧集文件混在剧根目录**；
* **特别篇插入某季**需要元数据里的 `airsbefore_season` / `airsafter_season` / `airsbefore_episode`
  （NFO 里同名标签），并且要在 仪表盘 → 库 → 显示 里打开"在所属季内显示特别篇"；
  同一位置多个特别篇按 S00 里的顺序播；
* **多版本**（同季同集）：`S01E01 - 1080p.mkv` / `- 720p.mkv` / `- Extended.mkv`。

### 2.3 外挂字幕/音轨的命名与标记（值得直接照搬）

`影片.default.srt`、`影片.forced.en.ass`、`影片.en.sdh.srt`、`影片.English Commentary.en.mp3`

| 类型 | 标记 |
|---|---|
| 默认 | `default` |
| 强制 | `forced`、`foreign` |
| 听障 | `sdh`、`cc`、`hi` |

* 多个标记用 `.` 串联；**认不出来的文字会拼成流的标题**（如 `English Commentary`）；
* `hi` 与印地语冲突：单独 `hi` = 印地语，`x.en.hi.srt` = 英语听障；
* **容器里有多个内嵌流时这些标记会被忽略**。

### 2.4 图片文件名（本地图优先于在线图）

| 文件名 | 类型 | 适用 |
|---|---|---|
| `poster`/`cover`/`folder`/`default`/`movie`（电影）/`show`（剧）/`thumb`（集，作后缀） | Primary 海报 | 电影/剧/季/集/音乐 |
| `backdrop`/`fanart`/`background`/`art`、`extrafanart/` 目录 | Backdrop 背景 | 电影/剧/季/音乐 |
| `banner` | Banner | 视频 |
| `logo`/`clearlogo` | Logo | 视频 |
| `landscape`/`thumb` | Thumb 缩略 | 视频 |

多张背景可加序号（`backdrop-1.jpg`、`backdrop2.jpg`）轮播；电影还能从**容器内嵌图**取
（`Embedded Image Extractor`）。

## 二·补 命名解析参考实现（**已用官方示例对拍通过**，含 5 个真实坑）

我把第二章的规则写成了可运行的 Python 解析器，并拿**官方文档里的每一个例子**对拍。
下面这份是**修完坑之后**的版本（完整文件在 `docs/研究/附件_命名解析.py`）。
对拍结果（左边是官方原文的例子）：

| 输入（官方示例） | 解析结果 |
|---|---|
| `Best_Movie_Ever (2019).mp4` | 电影｜Best Movie Ever｜2019 |
| `Movie (2021) [imdbid-tt12801262] - 2160p.mp4` | 电影｜Movie｜2021｜[imdbid-tt12801262]｜2160p |
| `Movie (2021) [imdbid-tt12801262] - Directors Cut.mp4` | 电影｜Movie Directors Cut｜2021｜[imdbid-…] |
| `Awesome 3D Movie (2022).3D.FTAB.mp4` | 电影｜Awesome Movie｜2022｜**3D-ftab** |
| `Movie Name-cd1.mkv` / `-cd2.mkv` | 电影｜Movie Name｜第1段 / 第2段 |
| `Series Name A S01E01-E02.mkv` | 集｜Series Name A｜S01｜**E01-E02** |
| `Series Name A S02E03 Part 1.mkv` | 集｜Series Name A｜S02｜E03｜第1段 |
| `S01E01 - 720p - Part 1.mkv` | 集｜(父目录名)｜S01｜E01｜第1段｜720p |
| `S01E01 Some Episode-thumb.jpg` | **非视频**（图片，别当一集） |
| `Making of …-behindthescenes.mp4` | 电影｜Making of …｜**番外** |
| `Season 01` / `Season 00` / `Specials` / `S01` / `5` | 季=1 / **季=0 特别篇** / **季=0 特别篇** / 季=1 / 季=5 |

**5 个真实坑（我全都是先写错、再被对拍抓出来的）**

1. **图片/字幕文件会被误当一集** —— `S01E01 Some Episode-thumb.jpg` 这种"缩略图"名字长得和一集一模一样。
   ⇒ 先按**扩展名**分流：只有视频后缀才走"影片/剧集"解析，`.jpg/.srt/.ass/.nfo` 另走标记提取。
2. **绝对集号兜底不能贪** —— 我一开始用"任意位置的孤立数字"当集号，结果
   `3D.FTAB`→E03、`cd1`→E01、`1080p`→E01 全都中招。
   ⇒ 只在**名字末尾/括号里的独立数字**才认（`剧名 07.mkv`），并且把多段/3D 片段先摘掉。
3. **片名里本来就带 3D** —— `Awesome 3D Movie (2022).3D.FTAB.mp4` 里第一个 `3D` 是片名的一部分。
   ⇒ **优先匹配带格式的 3D**（`3D.FTAB` / `3d-hsbs` / `3D_FTAB`…），找不到才认孤立的 `3D`。
4. **多版本判定别把标题算进去** —— `S01E01 - 1080p.mkv` 去掉版本标签后标题是空的，
   拿标题比较会得出"不是同一集"的错结论。⇒ 判定只看 **(季, 集)**（官方规则就是"同剧同季同集 = 同一集的多版本"）。
5. **清理不干净时不要退回原始文件名** —— 原始文件名里带清晰度/版本标签，拿它当标题会让
   同一集的两个版本变成两部片子。⇒ 宁可为空（界面显示"未知/待确认"），也不要猜。

**一个更重要的结论（这条能省掉一堆工作）**：对**番剧/字幕组**那种文件名，
自己写解析器基本是徒劳：

```
[爱恋字幕社][10月新番][葬送的芙莉莲][Sousou no Frieren][01][1080P][MP4][GB][简中].mp4
【喵萌奶茶屋】★10月新番★[药屋少女的呢喃][01][1080p][简日双语][招募翻译].mp4
The.Matrix.1999.2160p.BluRay.x265.mkv        ← 英文发布组的 tag 也一样难清（x265/BluRay/WEB-DL…）
```

我的解析器在前两条上**标题只能给出空/半成品**。这正是为什么：
* 弹弹play 的 `/api/v2/match` **收的是原始文件名**（服务端有全套规则和数据库）—— Animeko 就是把原始名直接递上去；
* Jellyfin 这类服务器**留了"手动识别（Identify）"入口**，识别不了就让人点一下。

⇒ **V2 的策略**：普通电影/剧集用本地解析（够用），**番剧一律"原样送匹配接口 + 让人确认"**，
别指望本地正则能猜对。

  * v3：`GET https://api.themoviedb.org/3/movie/11?api_key=<URL 编码后的 Key>`（Key 会进 URL/日志）；

* **限流（官方原文）**：2019-12-16 起**取消了旧的 40 次/10 秒**限制；现在的上限

* **缓存条款（官方 API 使用条款原文，必须遵守）**：
  > *Cache, for longer than 6 months, any information obtained through or from TMDB or the TMDB APIs.*
  即 **不得缓存超过 6 个月**；我们本地缓存的清理策略要按这条来（例如 30 天过期 + 上限 6 个月硬顶）。
* **署名（attribution）**：用了 TMDB 数据就要在界面上写清
  "This product uses the TMDB API but is not endorsed or certified by TMDB."（分册里有原文与位置建议）。
* 图片还涉及**按语言选图**（`include_image_language=zh,en,null`）与**选图打分**
  （`vote_average`/`vote_count`/`iso_639_1`/尺寸）—— 细节在分册 2.2/2.6。

## 四、给 V2 的落地蓝图（我们要真做的部分）

### 4.1 弹幕（照 Animeko 的分层，用 Python + Qt 重写）

```
wangpan/danmaku/
├── 模型.py        弹幕条目（时间秒/文本/模式/字号/颜色/来源/发送者）、弹幕池
├── 源/
│   ├── 接口.py    弹幕源协议：匹配(素材信息) → 剧集ID；取弹幕(剧集ID) → list[弹幕条目]
│   ├── 弹弹play.py  api.dandanplay.net（/api/v2/match、/api/v2/comment/{id}），带 AppID/签名
│   └── 本地.py     读取本地 .xml/.json 弹幕（离线/自备源）
├── 匹配.py        ① 文件名解析 → ② 送源匹配 → ③ 结果打分（编辑距离，照 Animeko）→ ④ 人工确认
├── 过滤.py        类型过滤 / 关键字 / 正则 / 发送者 / 顶部底部开关（正则规则分组持久化）
├── 轨道.py        滚动/顶部/底部三种轨道 + 防重叠 + **按长度调速度**（基准速度 88、间距 36、区域 0.25）
└── 渲染.py        QPainter 绘制（描边 + 颜色 + 字号倍率），按"帧时间平滑"推进，只在可见时间窗内取弹幕
```

细化要点（都来自上面的取证）：

1. **时间轴**：以播放引擎的 `当前时间秒` 为唯一时钟（我们已经有音频主时钟 + 系统时钟，
   天然支持暂停/倍速/跳转；跳转后要按新时间重新取可见弹幕，不要累积状态）；
2. **轨道算法**：每条轨道记录"最后一条弹幕的右边界 + 进入时间"，新弹幕满足
   `间距 ≥ 36` 且不与前一条追尾才放进去；放不进就找下一条轨道，找不到就丢弃（或按 Animeko 那样加速）；
3. **速度**：`速度 = 基准速度 × min(1.14, (文本宽度/基准宽度)^k)`（Animeko 用 log/pow 平滑），
   基准宽度按屏幕宽度的某个比例定，字号缩放后重算；
4. **性能**：弹幕按时间**排序 + 二分**取窗口；绘制只画当前窗口内的；文字宽度用 `QFontMetrics` 预计算并缓存
   （key = 文本 + 字号）；一帧只做一次 `QPainter`（我们字幕那次踩过"同一设备嵌套两个 QPainter 会整屏不画"）；
5. **云过滤**：先做本地规则（正则 + 关键字 + 类型），把"过滤规则"做成可导入导出（社区共享就是"云过滤"的雏形），
   真正的云端规则需要服务端，不建议自己造；
6. **发送弹幕**：要发到 DanDanPlay 需要 AppID/AppSecret 且**服务端签名**（分册确认后写死在源里），
   第一版建议**只读不发**，或只发到本地池。

### 4.2 刮削（照 Jellyfin 的规范扫描，用 TMDB 取数）

```
wangpan/scrape/
├── 命名解析.py   电影/剧集命名解析（严格按第二章规则：年份、[id]、SxxExx、E01-E02、Season NN、多版本/多段/番外）
├── 扫描.py       目录遍历 → 生成"待识别条目"（电影 / 剧集 / 季 / 集 + 关联的外挂字幕与图片）
├── tmdb.py       /search/movie|/tv → /movie|/tv/{id} → credits/images/release_dates|content_ratings
│                 语言回退：zh-CN → en-US → 原名；图片按 vote_average/iso_639_1 选，尺寸分级缓存
├── 库.py         SQLite：媒体/剧集/季/集/人物/媒体人物/图片/分级/外部ID（含 UNIQUE(媒体ID,来源,类型)）
├── 图片.py       下载 + 本地缓存（poster/backdrop/logo/profile 分级尺寸）+ 失败重试 + 并发限制
└── 集成.py       与播放器联动：海报墙点击播放、续播位置、字幕自动挂载
```

关键决策（都有依据）：

* **本地优先**：NFO/`poster.jpg`/`fanart.jpg`/同名 `.srt` 优先于在线数据（Jellyfin 的做法），
  在线数据只填空；
* **匹配打分**：先用 `[imdbid-tt…]`/`[tmdbid-…]` 精确命中（有则跳过搜索），否则
  `标题相似度 + 年份 + 类型`综合打分，低于阈值就**放进"待确认"列表**让人点一下（别自动认错片）；
* **分级**：电影用 `/movie/{id}/release_dates`，剧集用 `/tv/{id}/content_ratings`，
  按国家代码取（US 的 PG-13/R、CN、JP…），存进 `分级` 表并保留来源；
* **评分**：`vote_average` + `vote_count`（并记来源与抓取时间，避免把旧分数当新的）；
* **海报**：海报墙用小尺寸（`w200/w342`）+ 详情页用 `w500/original`，**分级缓存**，
  这是海报墙流畅的关键；列表滚动用预生成的缩略图，别在滚动时解码原图；
* **限流与合规**：TMDB 有速率限制（具体数字见分册）；**API Key 不进仓库**（放配置/环境变量）；
  界面上按 TMDB 要求做**署名**（"This product uses the TMDB API but is not endorsed…"）。

### 4.3 播放侧可以借鉴 Jellyfin/Emby 的三件事

1. **能力协商**：客户端上报"我支持什么"（容器/编码/字幕/码率），服务端给"怎么播"的决策。
   我们自己写播放器时，这个思路可以用来做**"直连 / 重封装 / 转码"三档决策**与**失败回退**；
2. **进度与续播**：`Playing/Progress`、`Playing/Stopped` 这种显式事件模型，
   比"每 N 秒存一次位置"更可靠（我们 V2 现在是 5 秒落盘 + 关窗落盘，够用但可以升级成"事件 + 落盘"双层）；
3. **Trickplay 进度预览**：预生成时间轴缩略图（我们已有"悬停解一帧"的按需版本，
   预生成是它的性能升级版：定时批量解码并存小图，滚动进度条时直接查表）。

## 七、四个项目研究完了：**决策要点**（只写会影响我们怎么做的）

四份分册（`Animeko_弹幕.md` 1716 行、`Jellyfin_播放与刮削.md` 5545 行、
`Emby_播放与刮削.md`、`Vidhub_与TMDB刮削底座.md` 2932 行）都是**源码/官方文档级**证据。
下面是我读完后的**结论性要点**（细节在分册，每条都有出处）：

### 7.1 弹幕（Animeko）
* 能照搬：**位置=帧时间纯函数**、防重叠判据（比"最小间距"更严谨）、轨道内二分插入、
  按长度调速（1.14^log2）+ 随机抖动、**每条预渲染位图缓存**、帧时间 PLL 平滑、时间轴语义（暂停停表、
  seek 阈值 3s×倍速、回溯 20s）、各默认常量（88 dp/s、36dp、0.25、18sp、描边 4f、固定弹幕 5000ms）；
* 不要抄：AGPL 代码（算法可以，代码不行）、"云过滤"（不存在）、"hash 匹配"（它没实现）。
* **我们能做得比它好**：弹幕列表可点击跳转、画布支持点击/长按（复制/举报/屏蔽该发送者）、
  进度条弹幕密度预览、多源去重、**自己实现 16MB MD5 提升匹配率**（官方规范支持）。

### 7.2 刮削（Jellyfin / Emby / TMDB）
* **TMDB 没有中国大陆分级**（电影 45 国、剧集 40 国，均不含 CN）—— 中文场景只能回退 HK/TW 或显示"暂无分级"；
  这条不查不知道，做界面时会一脸问号；
* `include_image_language` 要传 **`zh`** 而不是 `zh-CN`（图片不支持区域变体），且必须带 `null`；
* 剧集**全剧阵容**必须用 `/tv/{id}/aggregate_credits`（`/credits` 只有最新一季，且两者**结构不同**）；
  演员排序看 `cast[].order`（不是 `cast_id`）；
* `number_of_episodes` 与 `Σseasons[].episode_count` **对不上**（第 0 季 Specials 会污染）；
  判断季号**必须用 `season_number`**（`seasons[].name` 会随语言变成 "Staffel 1"）；
* `CommunityRating` 是 **0–10**，而 `CriticRating` 是 **0–100 且不归一化**（两者量纲不同，UI 要分开）；
  Jellyfin 的 `OfficialRating` 有格式规范：`[国家码-]分级值`，**US 不带前缀**，`DE-` 要改写成 `FSK-`；
* Jellyfin **核心没有内置片头/片尾识别**（只有插件接口 `IMediaSegmentProvider`）、
  **服务端没有字幕偏移**（纯客户端行为）、**没有码率阶梯表**（阶梯由客户端 `maxStreamingBitrate` 决定）；
* **本地 NFO 始终被读且始终优先**（没有"本地优先"开关这种东西）；
* 脏 provider id 要主动清除（Jellyfin 有白名单校验，否则每次刷新都会以同样方式失败）；
* 限流/条款（官方原文）：TMDB 约 **40 req/s**、**缓存不得超过 6 个月**、必须放英文署名；
  OMDb 免费 **1000 次/天** 且内容 **CC BY-NC 4.0**（商用注意）；TVDB v4 用 `POST /login` 换 **1 个月有效** JWT；
* **Emby 的边界（重要）**：`MediaBrowser/Emby` 只是 **3.5.3.0 快照**，而且
  `MediaBrowser.Model`/`Controller`/`Emby.Naming`/`Emby.Server.MediaEncoding` **都是二进制 DLL** ——
  **播放/转码在 3.5.3 就已闭源**；现行接口形状只能靠官方 OpenAPI（`swagger.emby.media/openapi.json`，
  标注版本 4.1.1.0）。认证头原文：`X-Emby-Authorization` 或 `Authorization`（等价），
  scheme 接受 `MediaBrowser` 或 `Emby`，键 `DeviceId/Device/Client/Version/Token`，
  token 回退顺序 `X-Emby-Token` → `X-MediaBrowser-Token` → `?api_key=`；
  Emby 还比 Jellyfin **多一个** `POST /Sessions/Playing/Ping`。
  （很多人以为是 Jellyfin 发明了 `Authorization: MediaBrowser ...`，其实 Emby 3.5.3 就已经同时接受两种头。）
* **Emby 现行 API 的权威源找到了**：`MediaBrowser/Emby.SDK` 仓库里的
  `Resources/OpenApi/openapi_v3.json` = **官方 OpenAPI 4.10.0.40（433 paths / 338 schemas）**，
  比 `swagger.emby.media`（只有 4.1.1.0 / 356 paths）新得多 —— 要写 Emby 客户端就看这份；
* **一个会直接坑到我们的差异**：`PlaybackInfo` 的参数位置两边**正相反** ——
  Emby 官方 JS 客户端把所有参数放 **query**、body 里只放 `DeviceProfile`；
  Jellyfin 12.x 把 15 个 query 参数全标 deprecated（改用 body）。
  ⇒ 兼容写法：**两边都放**；
* **码率阶梯在客户端算**（Emby 官方客户端：局域网直接 140 Mbps；公网依次下 500KB/1MB/3MB 测速
  → 取实测的 **70%** → 缓存 1 小时，用 `/emby/Playback/BitrateTest?Size=` 测速）——
  这解释了 Jellyfin/Emby 服务端为什么都没有"码率阶梯表"；
* **进度上报的官方节奏**：客户端**每 10 秒报一次 + 每次用户交互立刻报一次**，
  服务端自己在这两次之间**每秒插值**（我们的 V2 现在是 5 秒落盘，可以按这个改）；
* **命名/刮削的"最大公约数"**（Emby/Jellyfin/Kodi/Plex 四方都认）：
  `Name (Year)/Name (Year).ext`、`Series/Season NN/Series SxxExx.ext`、
  `Season 0|Season 00|Specials`、多版本用 `" - "` 后缀、ID 标签 `[tmdbid=xxx]`、
  NFO 用 `<视频名>.nfo` **优先**、图片 `poster/fanart/logo/thumb`；
* **Emby 的 `.strm` 是官方支持的**（`BaseVideoResolver` 判 `IsShortcut`）——
  这条对我们的网盘项目**直接有用**：给网盘里的片子在本地放一个 `.strm` 文本文件，
  媒体库就能"像本地文件一样"识别与刮削，播放时再把直链喂给播放器。

### 7.3 VidHub（顺带纠正与一个可直接复用的东西）
* 你给的 GitHub 链接是 **PHP 的 YouTube 克隆网站**（无刮削、无播放器逻辑）；
  真正的 VidHub 是**闭源 App**（南京欧米，`com.mac.utility.media.hub` v3.0.6）：
  官方原文确认 **TMDB 刮削**、连 **Emby/Jellyfin/Plex/SMB/WebDAV**、多网盘、HDR/杜比视界、
  字幕、**进度同步走 iCloud**、**含 Android**；
* ⚠️ App Store 上**有两个不同的 App 都叫 VidHub**（另一家是 MOBILE ALCHEMY LTD，`vidhub.app`）——
  看第三方评测时先核对 bundle id，否则一定张冠李戴；
* **可直接复用**：VidHub 公开了 URL-scheme 协议
  `open-vidhub://x-callback-url/play?url=&position=&sub=&filename=&x-success=&x-error=&x-cancel=`，
  `x-success` 回调会带 `position/duration/status: finished|stopped/request-id`。
  我们的网盘管理器要"交给外部播放器播"时，**照这套接口设计（或直接对接它）**比自己定协议省事得多；
* VidHub 官方说自动匹配**只看文件名、不看目录结构** —— 与"用 `Season 01/` 兜底"是取舍：
  我建议**主用文件名 + 目录仅兜底**（可预测性优先，错了让人工确认）。
