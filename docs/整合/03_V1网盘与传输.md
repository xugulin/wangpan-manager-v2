### 1.4 为什么走子进程（分工与动因）

代码给出三条理由（`核心/适配器.py:6-16`、`docs/架构设计.md` §1 约束 4）：

1. **顶层包名冲突（唯一的硬约束）**：三家适配器项目各自的顶层包都叫 `核心`（还有 `界面`）。在同一个解释器里 import 会互相覆盖，因此「把适配器原 GUI 嵌成一个页面」不可行。
2. **适配器源码一行不改**（`核心/适配器.py:9`）：V8_3 只做驱动与编排，通过协议调用。
3. **进程隔离顺带解决 PySide6/GC 陷阱**：适配器 `启动.py:11/19` 里都 `gc.disable()`，把 GC 关在一个可牺牲的子进程里，主进程不受影响。

分工：

| 关注点 | 主进程（`核心/`） | 桥子进程（`桥/`） |
|---|---|---|
| 任务编排/并发/重试/持久化 | ✅ `传输引擎.py` | ✗ |
| 网盘协议细节 | ✗ | ✅ `后端_*.py` + 适配器 `核心/` |
| 凭证读写 | ✗（只看文件是否存在，见 `界面/网盘页面.py:152`） | ✅ 只调适配器自己的仓库 API |
| 登录 GUI | 启动适配器原 GUI（`适配器规格.启动适配器GUI`178）或自绘 6 方式对话框 | ✅ `login_*` 命令 |
| 暂停的真实生效点 | 发 `pause_task` | ✅ 在进度回调里抛错（`工作进程.py:247`） |

### 1.5 请求 / 响应协议（消息格式与字段）

定义在 `桥/工作进程.py:7-11` + `核心/子进程客户端.py:170-252`。

**请求**（主进程 → 桥，stdin，一行一个 JSON，`子进程客户端.py:176-178`）：

```json
{"id": 1, "cmd": "list", "params": {"path": "/"}}
```

- `ensure_ascii=False`，`separators=(",", ":")`（紧凑，无空格）
- `id` 由 `itertools.count(1)` 生成（`子进程客户端.py:60`），单调递增
- **`cmd` 全清单**（`工作进程.py:126-245`）：
  `ping` / `close` / `account` / `list` / `stat` / `ensure_dir` / `delete` /
  `auth_caps` / `login_qr_start` / `login_qr_wait` / `login_qr_cancel` / `login_cookie` /
  `login_sms_send` / `login_sms_verify` / `login_token` / `login_password` / `login_email` /
  `logout` / `write_probe`（**可选能力**，`getattr` 探测，182-186）/
  `upload` / `download` / `play_link` / `pause_task` / `resume_task`
- **没有** `move` / `share` / `rename` 命令

**响应**（桥 → 主进程，stdout）：

```json
{"id": 1, "ok": true,  "result": [...]}
{"id": 1, "ok": false, "error": {"type": "PermissionError", "message": "..."}}
```

- 成功走 `result`（`工作进程.py:106`）；失败走 `error.type` / `error.message`（117-124）
- 客户端据 `error.type == "未登录"` 抛 `认证错误`，否则 `适配器错误`（`子进程客户端.py:212-222`）
  ⚠️ 注意：桥侧实际抛的是 `PermissionError` 等 Python 异常类名（`工作进程.py:121`），
  与客户端判断的字面量 `"未登录"` **不一致** —— 因此「未登录」目前不会走 `认证错误` 分支（**未确认**这是否为已知取舍）。

**事件推送**（无 `id`，靠 `event` 字段区分，`子进程客户端.py:238-251`）：

```json
{"event":"progress","task_id":"t1","phase":"download","current":123,"total":456}
{"event":"log","level":"info","message":"..."}
```

- `progress` → 查 `_进度回调[task_id]` 并回调 `(阶段, 当前, 总量)`（239-248）
- `log` → 交给日志回调（249-251）
- 桥的 **stderr 单独一条线程**按「信息/警告」级别上报终端（`子进程客户端.py:254-263`）

**握手 / 超时 / 中断语义**：

- `启动()` 末尾调 `ping`（超时 30s）确认后端导入成功（`子进程客户端.py:130`）
- `upload` / `download` 超时 = `None`（不限时）(308 / 351)；登录类 120–180s；`扫码等待` 比桥内截止多给 120s（395-406，注释解释「界面超时、桥稍后仍写入凭证」的错位）
- 桥进程退出/输出流结束 → `失败所有等待("适配器输出流结束")`（252），所有挂起 Future 收到 `适配器错误`

**两个实测踩坑**（注释里写明）：
- **必须用 `PurePosixPath` 而不是 `Path`**（97-100）：Windows 上 `Path("a:b.txt")` 把 `a:` 当盘符、`Path("a\b.txt")` 把 `\` 当分隔符，这两个非法字符就逃过改名了（真机 Windows CI 实测）。
- **秒传命中会绕过这层校验**（docstring `13-14`）：内容已存在时百度秒传不走 `/api/create`，所以「同一个文件重传一次居然成功」是假象，第一次真实上传才是真相。
